# 「無料枠の90%を使い切った」と言われたが、そんなに使った覚えがない（前編・原因究明）

朝、Cloudflareからこんなメールが届いていた。

> お客様のアカウントは、D1無料ティアの1日あたりの上限（5000000 rows_read）の90%を使用しました。2026-09-20 at 00:00:00 UTCまでに上限を超えた場合、D1リクエストはエラーを返します。

D1というのはCloudflareが提供しているデータベースサービスで、無料で使える代わりに「1日に読み取れる行数は500万行まで」という制限がある。それを90%使い切った、つまり450万行読んだ、と言われている。

心当たりがない。運用しているのはマラソン大会のポータルサイト「HASHIRU」で、個人開発だし、登録されている大会は133件しかない。1日のアクセスも数千程度のはずだ。それで450万行はどう考えても多すぎる。

結論から言うと、**原因はアクセス数ではなく「1回のページ表示で読む行数」だった**。1回の表示で約5,300行読んでいた。これを1,200行台まで減らした。その過程で、知らないと絶対に気づけない落とし穴をいくつか踏んだので記録しておく。

## まず「本当に使っているのか」を確かめる

推測で手を動かす前に、実測する。Cloudflareのコマンドラインツール `wrangler` には、データベースの使用状況を出すコマンドがある。

```
npx wrangler d1 info krote-run-db
```

```
name                    krote-run-db
num_tables              32
database_size           913 kB
read_queries_24h        38,919
rows_read_24h           4,438,892
rows_written_24h        5,914
```

メールの通り、24時間で4,438,892行読んでいる。上限500万に対して89%。

ここで目を引くのは `database_size` の **913 kB** という数字だ。データベース全体でも1MB足らずしかない。にもかかわらず1日444万行読んでいる。

ざっくり言えば、**データベースの中身を1日に何千回も丸ごと読み直している**ということになる。これはアクセスが多いのではなく、明らかに読み方がおかしい。

## そもそも「rows_read」とは何か

ここで大事な前提がある。Cloudflareが課金・制限の単位にしている `rows_read` は、**「結果として返した行数」ではなく「探すために走査した行数」**だ。

たとえば1,000人分の名簿から「田中さん」1人を探す場合を考える。

- 名簿が五十音順に並んでいて、索引（インデックス）から一発で引ける → 読んだ行数は**1行**
- 名簿がバラバラの順で、先頭から1件ずつ「田中さんですか？」と確認していく → 読んだ行数は**1,000行**

どちらも返ってくる結果は「田中さん1人」で同じ。でもコストは1000倍違う。これがrows_readの考え方で、「返ってくるデータが少ないから安いはず」という直感が通用しない理由でもある。

## 犯人を特定する

`wrangler` には、どのクエリ（データベースへの命令）がどれだけ行を読んだかを集計するコマンドもある。

```
npx wrangler d1 insights krote-run-db --timePeriod=1d --sort-by=reads
```

上位5件で、その日の読み取りの約342万行を占めていた。

| クエリの内容 | 1日の実行回数 | 合計読み取り行数 | 1回あたり |
|---|---|---|---|
| 「大会の種目」を全件取得 + 並べ替え | 3,018 | 1,547,752 | 512 |
| 「エントリー期間」を全件取得 + 並べ替え | 1,727 | 863,104 | 499 |
| 「参加賞」を全件取得 | 3,238 | 423,626 | 130 |
| 「もうすぐ募集開始の大会」の検索 | 704 | 340,712 | 483 |
| 「募集中の大会」の検索 | 561 | 245,787 | 438 |

実行回数から逆算すると、サーバーがページを組み立てた回数は1日数千回。つまり**1回あたりのコストが異常**なのだと確定した。

（なお、この「数千回」の正体は後編の最後で引っくり返る。人間のアクセス数とは全然違う数字だった。）

ここから3つの原因が見つかった。

## 原因1: 8件しか表示しないのに、全部読んでいた

トップページには「もうすぐ開催」「募集中」「もうすぐ募集開始」という3つのセクションがあり、それぞれ6〜8件の大会カードを並べている。

このデータの取り方がこうなっていた。

1. 条件に合う大会を取ってくる
2. **全大会の種目を全件取ってくる**
3. **全大会のエントリー期間を全件取ってくる**
4. **全大会の参加賞を全件取ってくる**
5. プログラム側で「この大会のぶんだけ」に絞り込んで組み立てる

つまり、8件表示するために全133大会分の関連データを毎回読んでいた。しかもこれが3セクション分、独立に走る。

なぜこんな作りになっていたかというと、データベース側で結合（JOIN）せずに、必要そうなテーブルを丸ごと持ってきてプログラム側で突き合わせる方が実装がシンプルだからだ。データが少ないうちは気にならないし、動作も速い。行数で課金される環境でだけ牙をむく。

直し方は素直で、「まず表示する大会を8件に絞ってから、その8件のIDだけを条件にして関連データを取る」という2段構えにした。

実測した効果がこれ。

| | 変更前 | 変更後 |
|---|---|---|
| 種目テーブル | 514行 | **36行** |

## 原因2: 並べ替えただけで、読んだ行数が2倍になる

これが今回いちばん厄介だった落とし穴。

「大会の種目」テーブルの中身は実際には**257行**しかない。それなのに、集計では1回あたり**512行**読んだことになっている。ちょうど2倍。

原因は `ORDER BY`、つまり並べ替えだった。同じテーブルに対して、並べ替えの有無だけを変えて実測してみる。

```sql
SELECT * FROM race_categories ORDER BY sort_order  → rows_read = 514
SELECT * FROM race_categories                      → rows_read = 257
```

きれいに2倍になっている。

理由はこうだ。並べ替えの基準にしている列に索引がないと、データベースは「全部読む」→「並べ替えのために作業用の領域にコピーして、そこをまた全部読む」という動きをする。**この作業のぶんまでrows_readに計上される**。

これは請求額を見ているだけでは絶対に気づけない。「並べ替えを指示しただけで倍のコストになる」とは普通は思わないからだ。

対処は2通りある。索引を足すか、並べ替えをやめるか。今回はどのみちプログラム側でデータを組み立て直していたので、**並べ替えもプログラム側でやる**ことにした。数百件を並べ替えるくらいはJavaScript側では一瞬で終わる。

## 原因3: 同じデータを2回取りに行っていた

大会の詳細ページには、もうひとつ地味な無駄があった。

Webページには「タイトルタグ」や「SNSでシェアしたときに出る説明文」といったメタ情報があり、Next.jsではこれを本文とは別の関数で組み立てる。この2箇所がそれぞれ独立に「この大会の情報をください」とデータベースに問い合わせていた。

1回の表示で、18本のクエリのセットが2回走っていたことになる。

これはReactの `cache()` という仕組みで解決できる。同じリクエストの中で同じ関数が複数回呼ばれたら、1回目の結果を使い回すというもの。関数を包むだけで済む。

## 前編の結果

3つを直した結果を、本番のデータベースに対して実測した。

| 対象 | 変更前 | 変更後 |
|---|---|---|
| **トップページ1表示** | **約5,257行** | **約1,247行（-76%）** |
| 種目テーブル（全件） | 514行 | 257行 |
| 種目テーブル（8大会ぶん） | 514行 | 36行 |
| サイトマップ | 約1,700行 | 133行 |
| 大会詳細1表示 | 同じ取得を2回 | 1回 |

1日444万行のうち、およそ4分の3が消える計算になる。

## 今回の教訓

- **無料枠は「量」ではなく「設計」で決まる**。アクセスが少なくても、1回あたりが重ければ簡単に上限に届く
- **rows_readは「探した行数」**。返ってくるデータの量と一致しない
- **並べ替えにもコストがかかる**。索引のない列で並べ替えると、読んだ行数が2倍に計上される
- **推測せずに計測する**。`wrangler d1 insights` で「どのクエリが何行読んだか」が分かるので、犯人探しは実は一瞬だった

ただし、これで終わりではない。1回あたりのコストは4分の1になったが、**リクエストが来るたびにデータベースを読みに行く構造そのもの**は何も変わっていない。同じページを100回表示すれば100回データベースを読む。

# 「無料枠の90%を使い切った」と言われたが、そんなに使った覚えがない（後編・キャッシュ編）

[前編](./blog-d1-rows-read-1-cause.md)では、1回のページ表示で約5,300行もデータベースを読んでいた原因を3つ潰して、1,200行台まで減らした話を書いた。

ただし、前編で直したのは「1回あたりのコスト」だけだ。**リクエストが来るたびに毎回データベースを読みに行く構造**は手つかずのまま残っている。同じトップページを100回表示すれば、100回データベースを読む。

本来これはキャッシュが解決する問題だ。「1回読んだ結果をしばらく使い回す」ようにすれば、100回表示しても読むのは1回で済む。

ところがこのサイトでは、**キャッシュが完全に無効になっていた**。

## 設定ファイルに書かれていた "dummy"

このサイトは Next.js というフレームワークで作られていて、Cloudflare上で動かすために OpenNext というツールを挟んでいる。その設定ファイルを見ると、こうなっていた。

```ts
incrementalCache: "dummy",
tagCache: "dummy",
queue: "dummy",
```

`dummy` は「何もしない実装」を意味する。具体的には**「キャッシュを読む」と言われたら常に「ありません」と答え、「キャッシュに保存して」と言われたら何もしない**というダミーの部品が入っている状態だ。

これは初期構築時に、ひな形のまま深く考えずに設定したものだと思われる。エラーも警告も出ないし、サイトは正常に動く。ただ全リクエストが毎回データベースに到達するだけだ。

つまり、前編で見つけた「1回5,300行」は、キャッシュが効いていれば大して問題にならなかった。**2つの問題が重なって450万行になっていた**ことになる。

## Next.jsのキャッシュは1か所にまとまっている

ここで少し仕組みの話をする。

Next.jsには「インクリメンタルキャッシュ」と呼ばれる保管庫がひとつあって、性質の違う3種類のデータが全部そこに入る。

| 種類 | 何が入るか |
|---|---|
| ページ | ページを組み立てた結果そのもの（HTML） |
| データ | 外部APIやデータベースから取ってきたデータ |
| その他 | 新しい記法向けの保存領域 |

重要なのは、**この3つが同じ保管庫を共有している**こと。だから `"dummy"`（保管庫なし）にすると、ページキャッシュもデータキャッシュも一緒に死ぬ。「うちはページキャッシュを使っていないから関係ない」と思っていると、データキャッシュまで無効になっていることに気づけない。

なぜこんなに差し替え可能な作りになっているかというと、Next.jsの標準のキャッシュは「サーバーのディスクにファイルとして保存する」前提だからだ。Cloudflareの実行環境にはディスクがない。おまけにリクエストごとに世界中の別々のデータセンターで処理されるので、メモリに置いても他のリクエストからは見えない。だから保存先を自分で指定してやる必要がある。

## 本命だった「ページまるごとキャッシュ」は使えなかった

最初に狙ったのは、当然ながら**ページまるごとのキャッシュ**（ISR）だった。ページを組み立てた結果を保存しておいて、次の人には作り直さずにそれを返す。これならデータベースを読まないどころか、ページを組み立てる計算そのものが省ける。

ページに1行足すだけで有効になる。

```ts
export const revalidate = 3600;  // 1時間キャッシュ
```

これができなかった。理由は、**この1行を足すとNext.jsがビルド時にページを先に作ろうとする**からだ。

ビルドというのはデプロイ前にプログラムを組み立てる工程で、これは開発者の手元やCI上で走る。そのときCloudflareのデータベースは存在しない。当然、ページを組み立てようとしてデータベースに接続しようとした時点で失敗する。

抜け道もあるにはあった。OpenNextには「ビルド時でもデータベースに繋ぎにいく」モードがある。しかしこれは**手元のローカルデータベースに繋ぎにいく**。開発用の中途半端なデータが、本番ページに焼き付いてデプロイされることになる。これは論外だ。

調べているうちに、なぜこのサイトの全ページが「毎回組み立て直し」になっているのか、その直接の原因も分かった。多言語対応に使っているライブラリが、専用の初期化関数を呼んでいないと「このページはリクエストごとの情報に依存している」と判断する仕様で、その関数がどこにも書かれていなかった。

つまりISRに進むには、多言語対応の作法の修正と、ビルド時にデータベースを見なくて済む構造への組み替えがセットで必要になる。今日中に無料枠が尽きるかもしれない状況でやる規模ではない。

## 方針転換: ページではなくデータをキャッシュする

そこで、ページを組み立てる工程は毎回走らせたまま、**データベースから取ってくる部分だけをキャッシュする**ことにした。

```
これまで: リクエスト → ページ組み立て → データベース（毎回）
これから: リクエスト → ページ組み立て → キャッシュ（DBは1時間に1回だけ）
```

ページ組み立ての計算は毎回走るので、CPU時間の節約にはならない。ただし今回の問題はデータベースの読み取り行数なので、狙いは完全に達成できる。しかもビルド時にデータベースを触らないので、さっきの詰みも回避できる。

CPU側については、Cloudflareの無料枠が1日10万リクエストなのに対して実際は1日4,000程度なので、そもそも困っていない。

## どこに保存するか

保存先には R2 というCloudflareのファイル保管サービスを選んだ。無料枠が月1,000万回の読み取りと潤沢で、このサイトの規模なら1桁余る。

さらにその手前に、もう1段キャッシュを挟んだ。

```
リクエスト
  └─ ① データセンター内の一時キャッシュ（最大60秒）
      └─ ② R2（1時間）
          └─ ③ 両方外れたときだけ データベース
```

①は、アクセスが集中したときに同じデータセンター内で短時間だけ結果を使い回す層。②が本体の保管庫になる。

## 踏んだ罠1: 「今日」をキャッシュしてしまう

実装中に気づいた、地味だが致命的な問題がある。

トップページの「募集中の大会」は、**今日の日付**を条件に検索している。この関数の結果をそのまま1時間キャッシュすると、こういう事故が起きる。

> 23時50分にキャッシュが作られる → 日付が変わって0時を過ぎる → 0時50分までの1時間、「昨日の日付で判定した結果」が表示され続ける

キャッシュというのは「同じ入力なら同じ出力」を前提にした仕組みで、関数の中でこっそり現在時刻を見るものとは相性が悪い。

解決策は、**日付を関数の外で取得して、引数として渡す**こと。

```ts
// 悪い例: 関数の中で今日を取る → 日付が変わってもキャッシュが残る
cache(async () => { const today = 今日(); ... })

// 良い例: 外で取って引数で渡す → 日付が変わると別のキャッシュ扱いになる
const 中身 = cache(async (today) => { ... })
export const 関数 = (limit) => 中身(今日(), limit)
```

キャッシュの識別子には引数が含まれるので、日付が変われば自動的に別のキャッシュとして扱われ、日付境界で勝手に切り替わる。「変わってほしくないものは中に隠す、変わってほしいものは引数に出す」と覚えておくといい。

ついでに、ユーザーが投稿したデータを集計する機能（大会ごとのランナーの装備統計）は、あえてキャッシュ対象から外した。自分が装備を公開した直後にサイトに出てこないと、壊れていると思われるからだ。

## 踏んだ罠2: キャッシュが効いているかを確かめる方法

ここが意外と難しかった。

まず保存先のR2を覗いて、ファイルが増えていれば成功、と考えた。

```
npx wrangler r2 bucket info krote-run-cache-stg
  object_count: 0
```

0件。失敗したのか？

確かめるために、**自分で手動でテスト用のファイルを1個置いてから、もう一度同じコマンドを叩いてみた**。

```
object_count: 0
```

置いた直後でも0のまま。つまりこの数字は**遅れて反映される統計値**で、今まさに書き込まれたかどうかの判定には使えない。危うく「R2への保存に失敗している」と誤診するところだった。

そこで、時間を使った間接的な確認に切り替えた。前段の一時キャッシュは最大60秒で消える。ということは、**15分放置してからアクセスして、それでもデータベースを読まなければ、R2から返ってきた証拠になる**。

検証環境にデプロイして実測した結果がこれ。

| 操作 | データベースの読み取り増加 |
|---|---|
| トップページ × 10回（1回目） | 1,251行 |
| トップページ × 10回（数分後） | **0行** |
| 大会詳細3種類 × 3回ずつ | 552行（3種類の初回のみ） |
| **15分放置してから1回ずつ** | **0行** |

10回表示して1回分しか読んでいない。15分放置後もゼロ。狙い通りに動いている。

## キャッシュはいつ消えるのか

「1時間キャッシュ」と聞くと、「大会情報を更新しても1時間反映されないのか」と心配になる。ここは実はうまくできている。

キャッシュの保存名には**ビルドID**が含まれている。デプロイのたびにこのIDが変わるので、**デプロイした瞬間に古いキャッシュは全部参照されなくなる**。

このサイトの更新手順は「クロールでデータ収集 → ファイルをコミット → デプロイ」なので、更新すれば必ずデプロイが走る。つまり実運用では即座に反映される。1時間のTTLが効くのは「デプロイせずにデータベースだけ直接書き換えた」という例外的なケースだけだ。

逆に注意点として、**古いビルドIDのファイルは誰も消してくれない**ので、放っておくとR2にゴミが溜まっていく。自動削除ルールを設定しておくのが定石になる。

## まとめ

2本合わせての結論はこうなる。

- 1日444万行の内訳は、「1回あたりが重い」×「毎回読みに行く」の掛け算だった
- 前編で1回あたりを4分の1に、後編で読みに行く回数をほぼゼロにした
- 最終的に、無料枠500万行に対して数万行のオーダーに収まる見込み

個人開発で無料枠を使っていると、「アクセスが少ないから大丈夫」と思いがちだ。でも実際に効いてくるのは**アクセス数ではなく設計**で、しかも今回のように、**知らないと気づけない仕様**（並べ替えで行数が2倍、ダミーのキャッシュ設定、遅延反映の統計値）がいくつも絡んでくる。

上限通知は不愉快だったが、結果的には「動いてはいるが無駄の多い実装」を炙り出してくれた。動いているコードのおかしさに気づくのは難しい。数字が教えてくれるうちは、まだ運がいい。

# 追記: 本当の主犯は「リンクの先読み」だった

ここまでで問題は解決した。ただ、ひとつ引っかかっていたことがある。

**そもそも、誰がこんなにアクセスしているのか。**

前編で「サーバーがページを組み立てた回数は1日数千回」と書いた。個人開発のサイトとしては多い。当初は「AIのクローラーに大量に巡回されているのでは」と疑っていた。だとすれば `robots.txt` を置くのが先だ。

確かめるため、本番サーバーのアクセスログを実際に採取してみた。

```
npx wrangler pages deployment list --project-name krote-run
npx wrangler pages deployment tail <本番デプロイID> --project-name krote-run --format json
```

Cloudflareでは過去のログを遡って見るには有料プランが要るが、**今この瞬間から流れてくるログを眺めるだけなら無料でできる**。26分ほど流しっぱなしにして、162件のリクエストを拾った。

## 結果: ボットはほとんどいなかった

送信元ごとに分類すると、こうなった。

| 送信元 | 件数 |
|---|---|
| 日本の一般ISP・Edge（Windows） | 81 |
| ベルギーの一般ISP・Chrome（Android） | 57 |
| Appleのネットワーク・Safari（Mac） | 14 |
| bingbot | 4 |
| ClaudeBot | 3 |
| Baiduspider | 3 |

ボットは**合計10件、全体のわずか6%**。1日換算でも500件程度で、負荷としては誤差だ。しかも `sitemap.xml` を読んでから巡回しており、行儀も悪くない。疑ってすまなかった。

残りの152件は、**普通の人間3人がブラウザでサイトを見ていただけ**だった。

## 1人がページを1枚開くと、152リクエスト飛ぶ

ここで妙なことに気づく。81件を送ってきた日本のIPは、**32秒間**にそれを集中させている。人間の操作にしては速すぎる。

中身を分解すると、正体が分かった。

| 種別 | 件数 |
|---|---|
| 実際に開いたページ | **1** |
| CSS・JavaScript・フォントなどの部品 | 53 |
| **先読み（プリフェッチ）** | **25** |
| ログイン状態の確認API | 2 |

**実際に開いたのは大会詳細ページ1枚だけ**。残りは全部おまけだ。

問題は「先読み」の25件だった。宛先を見ると、こうなっている。

```
/ja  /ja/races  /ja/calendar  /ja/news  /ja/guide  /ja/about
/ja/contact  /ja/terms  /ja/privacy  /ja/cookie-policy  /ja/sitemap  /ja/mypage
```

ヘッダーとフッターに並んでいるナビゲーションリンク、**全部**。

## Next.js は画面内のリンクを勝手に先読みする

これは Next.js の仕様だ。`<Link>` というコンポーネントで作ったリンクは、**画面に表示された時点で、リンク先のページを裏で先に取得しておく**。クリックしたときに一瞬で表示されるようにするための親切機能だ。

普通のサイトなら、これはありがたい機能でしかない。ただ今回は条件が悪かった。

- ヘッダーとフッターは**全ページに出る**。つまりどのページを開いても、ナビゲーションリンク全部が先読みされる
- 先読み先には `/ja/races`（大会一覧）と `/ja/calendar`（カレンダー）が含まれる
- この2ページは**全大会のデータを読み込む**、サイトで最も重いページ

計算するとこうなる。

> 人間が実際に開いたページ **3枚** に対して、サーバーがページを組み立てた回数 **41回**（実ページ3 + 先読み38）

**1ページ見るたびに、本人が見てもいない12ページぶんが裏で作られていた。** うち大会一覧とカレンダーだけで約3,400行のデータベース読み取りを発生させる。

前編で「1日数千回のレンダリング」と書いた数字の正体はこれだった。人間のアクセス自体は1日数百回程度で、**13倍に増幅されていた**だけだった。

## 対策: 重いページだけ先読みをやめる

先読みを全部切ればリクエストは激減するが、代わりにページ遷移が遅くなる。せっかくの機能を捨てるのはもったいない。

そこで、**重い2ページだけ先読みの対象から外した**。Next.js の `<Link>` には `prefetch={false}` という指定がある。

```tsx
<Link href="/races" prefetch={false}>大会一覧</Link>
```

軽いページ（利用規約やお知らせなど、そもそもデータベースをほとんど使わない）は先読みを残したので、体感速度への影響は小さい。それでいて、増幅されていたデータベース読み取りの大半が消える。

## 順番を間違えていた

振り返ると、今回の調査は**取りかかる順番が逆だった**。

1. クエリを軽くした（前編）
2. キャッシュを効かせた（後編）
3. **そもそも誰がなぜ呼んでいるのかを調べた** ← 最後

3番を最初にやっていれば、「重いページの先読みを止める」という一行の変更で問題の大半が消えていたかもしれない。

もっとも、1と2が無駄だったわけではない。先読みを止めても人間のアクセスぶんは残るし、クエリが軽くてキャッシュが効いているほうが健全だ。ただ、**「処理を速くする」より前に「その処理は本当に必要か」を問う**ほうが、ふつうは効率がいい。

ログを見るのに必要だったのはコマンド1本と26分の待ち時間だけだった。もっと早くやればよかった。
